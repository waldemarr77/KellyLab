# KellyLab

Backend для підготовки до технічних співбесід. Робочий сценарій: реєстрація → профіль → сесія → імпорт питань → відповіді → власні правки → експорт у TXT, PDF або DOCX.

## Що працює

- Реєстрація через email з підтвердженням пошти, JWT access/refresh, редагування посади та рівня.
- Зміна й відновлення пароля через пошту, видалення акаунта.
- Сесії та картки питань, доступні лише власнику.
- Імпорт тексту або UTF-8 TXT: одне питання на рядок, максимум 50 питань, 2000 символів на питання та 100 KB на файл. Повторний імпорт у заповнену сесію відхиляється.
- Генерація через Celery + Redis; для локального запуску можна виконувати задачі синхронно.
- Генерація відповідей Gemini через `google-genai`.
- Окреме зберігання AI-відповіді та власної відповіді; повторна генерація зберігає власні правки.
- TXT-експорт одразу у відповіді; PDF/DOCX — фоновою Celery-задачею через окремий Exporter service.
- Swagger, інтеграційні тести й CI з PostgreSQL.

Це API-MVP. React, parser колеги, AI-практика, перевірка коду, pgvector та Llama fallback ще не підключені. Модель `practice` залишається заготовкою. Exporter service розробляється окремо (гілка `feature/fastapi-exporter`); без нього PDF/DOCX-експорт завершується `failed`. TXT-експорт формується одразу без запису `Export`. LangChain/LangGraph поки не потрібні для одного виклику моделі.

## Локальний запуск у PowerShell

Спочатку в наявному `.env` задай `GEMINI_API_KEY` і `GEMINI_MODEL` (дивись нижче). З наявним `venv`:

```powershell
$env:USE_SQLITE = 'true'
$env:CELERY_TASK_ALWAYS_EAGER = 'true'
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py runserver
```

Існуючий `.env` не змінювався. Змінні поточного процесу мають пріоритет. На чистій машині потрібен Python 3.13: `python -m venv venv`, потім `.\venv\Scripts\python.exe -m pip install -r requirements-dev.txt`. Скопіюй `.env.example` у `.env`, лише якщо власного `.env` ще немає. `requirements.txt` містить залежності застосунку, `requirements-dev.txt` додає інструменти розробки (ruff).

Відкрий http://127.0.0.1:8000/api/docs/. У Swagger після отримання JWT натисни **Authorize** і введи `Bearer <access>`.

В іншому PowerShell можна запустити весь сценарій:

```powershell
.\examples\smoke-test.ps1
```

Скрипт створює окремого користувача, імпортує `examples/questions.txt`, робить п'ять справжніх запитів до Gemini і записує `examples/smoke-export.txt`. Пароль і токени не виводяться. Без ключа або ID моделі генерація завершиться помилкою; підстановки відповідей немає.

## Docker: PostgreSQL + Redis + Django + Celery

```powershell
docker compose --env-file .env up --build
```

Міграції виконує окремий сервіс перед стартом web/worker. API: http://127.0.0.1:8000/api/docs/. PostgreSQL і файли експорту (`media/`) зберігаються в named volumes `postgres_data` і `media`; `media` спільний для `web` (віддає файл) і `worker` (записує його). `docker compose down` зупиняє сервіси, зберігаючи дані; `docker compose down -v` видаляє і їх. Це конфігурація для локальної розробки, з Django development server.

Усі змінні з `.env` потрапляють у контейнери (`env_file`), тож ліміти, `CORS_ALLOWED_ORIGINS` тощо діють і в Docker. Винятки — адреси БД, Redis, кешу, Exporter і `USE_SQLITE`/`CELERY_TASK_ALWAYS_EAGER`: `compose.yaml` задає їх сам, бо значення з локального `.env` (`127.0.0.1`) у контейнері не працюють. Після зміни `.env` перезапусти сервіси: `docker compose up -d`.

Exporter у compose ще не доданий: worker звертається до `http://host.docker.internal:8002`, тобто до Exporter, запущеного на твоїй машині на порту 8002. Іншу адресу задай змінною `COMPOSE_EXPORTER_URL` у `.env`.

## Справжні AI-відповіді

У `.env` або змінних середовища встанови:

```dotenv
GEMINI_API_KEY=your-key
GEMINI_MODEL=model-id-available-to-your-account
```

Перезапусти Django і worker; у Docker використай `docker compose --env-file .env up --build` із власними значеннями. Якщо секрет містить `$`, у dotenv візьми його в одинарні лапки, щоб Compose не сприйняв частину секрету як змінну. ID моделі задається явно, оскільки доступність залежить від акаунта. Питання, посада та рівень надсилаються в API Google; запити можуть бути платними. SDK використовується за [офіційною документацією Google](https://googleapis.github.io/python-genai/).

Для фонового режиму поза Docker потрібні Redis і `CELERY_TASK_ALWAYS_EAGER=false`; worker: `celery -A config worker -Q celery,ai --concurrency=1 --prefetch-multiplier=1 --loglevel=info` у Linux/WSL (без `-Q celery,ai` генерація зависне в `processing`). Для локального запуску на Windows простіше eager або Docker. Eager блокує HTTP-запит до завершення генерації, але теж звертається до справжнього Gemini.

## API

У захищених запитах передавай `Authorization: Bearer <access>`.

Access діє 15 хвилин, refresh — 7 днів. Кожен виклик `token/refresh/` повертає новий refresh, а старий одразу відкликається, тому зберігай новий. Якщо refresh не використовувати 7 днів, потрібен повторний вхід. Після `logout/` refresh більше не працює, але вже виданий access діє до кінця своїх 15 хвилин. Прострочені записи blacklist прибирає `python manage.py flushexpiredtokens`.

Генерація має два ліміти на користувача, обидва з `.env`. `GENERATE_THROTTLE_RATE` (типово `2/minute`) обмежує частоту запусків `generate/`. `AI_DAILY_QUESTION_LIMIT` (типово 100) — скільки питань за добу можна надіслати в Gemini; квота списується при запуску, а питання, які так і не потрапили в Gemini (черга недоступна, запуск зупинився на помилці), повертаються; оновлюється о 00:00 UTC. Крім того, `AI_GLOBAL_DAILY_QUESTION_LIMIT` (типово 400) обмежує питання від усього сервісу, бо ключ Gemini спільний і має 500 запитів на добу (повтори після помилок теж списуються, тому ліміт нижчий). Він оновлюється опівночі за тихоокеанським часом, як і квота Google, тобто о 07:00/08:00 UTC. В усіх випадках API повертає `429`, а сесія не переходить у `processing`. Лічильники видно в адмінці, розділи «Лічильники» і «Загальні лічильники»; там же квоту можна скинути.

Генерація доступна лише після підтвердження пошти, інакше `generate/` повертає `403`: реєстрація відкрита, і без цього кілька нових акаунтів вичерпали б спільну квоту. Після реєстрації приходить лист із посиланням `EMAIL_VERIFICATION_URL` (сторінка фронтенду, яка надсилає `uid` і `token` на `verify-email/`). Без `EMAIL_HOST` листи друкуються в консоль `web`; для справжньої пошти задай `EMAIL_HOST`, `EMAIL_PORT`, `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, `DEFAULT_FROM_EMAIL`. Акаунти, створені до появи підтвердження, міграція позначає підтвердженими; вручну статус змінюється в адмінці. `register/` відповідає однаково (`202`) і для нової, і для зайнятої пошти, а власник зайнятої отримує лист, тож перевірити існування акаунта через API не вийде.

Створення сесій та імпорт обмежує `SESSION_WRITE_THROTTLE_RATE` (типово `60/hour` на користувача), а кількість сесій — `MAX_SESSIONS_PER_USER` (типово 50). Файл імпорту більший за 100 KB обривається під час завантаження, без прийому всього тіла (`400`). У production перед Django однаково постав nginx із `client_max_body_size 1m`.

Лист відновлення пароля веде на `PASSWORD_RESET_URL` (сторінка фронтенду, що надсилає `uid`, `token` і `new_password` на `password/reset/confirm/`). Посилання діє, доки пароль не змінено, але не довше 3 днів (`PASSWORD_RESET_TIMEOUT` Django); відновлення заодно підтверджує пошту. Після зміни чи відновлення пароля всі refresh-токени потрапляють у blacklist, а вже видані access-токени діють до кінця свого терміну (15 хвилин). Ендпоінти відновлення, зміна пароля й видалення акаунта мають ліміт `AUTH_THROTTLE_RATE`.

Невдалі входи через API та адмінку рахуються за email (`LOGIN_FAILURE_LIMIT_PER_EMAIL`, типово 5) і за IP (`LOGIN_FAILURE_LIMIT_PER_IP`, типово 20). Після ліміту пароль 15 хвилин не перевіряється: API повертає `429`, адмінка — звичайну помилку входу. Зворотний бік: стороння людина може на 15 хвилин заблокувати вхід на чужу пошту.

Ліміти частоти рахуються за IP. `NUM_PROXIES` — кількість проксі перед Django: `0` (типово) означає, що `X-Forwarded-For` ігнорується і береться адреса з'єднання; за nginx чи балансувальником вкажи точну кількість, інакше клієнт зможе підмінити IP заголовком. `token/refresh/` і `logout/` мають окремий ліміт `TOKEN_THROTTLE_RATE` (типово `30/minute`), щоб оновлення токенів не з'їдали спроби логіну. Лічильники зберігаються в кеші: у production задай `CACHE_URL` (Redis; у `compose.yaml` це `redis://redis:6379/1`), бо без нього кожен процес має власні лічильники, які скидаються після рестарту.

Між запитами до Gemini воркер робить паузу `AI_MIN_INTERVAL_SECONDS` (типово 4 с, бо free tier дозволяє 15 запитів на хвилину), тому сесія з 50 питань генерується приблизно 3–4 хвилини. Якщо Gemini все ж повертає `429`, повторна спроба йде через 30 с, щоб встигло скинутися хвилинне вікно. Ліміт рахується на весь ключ, а пауза — в межах однієї задачі, тому генерація йде в окрему чергу `ai`, яку обслуговує один процес (`worker-ai` у `compose.yaml`). Не запускай кілька AI-воркерів і не піднімай їм `--concurrency`: сесії тоді генеруватимуться паралельно й перевищать 15 RPM. Сесії чекають у черзі одна за одною; якщо черга довша за 10 хвилин (`GENERATION_STALE_AFTER`), сесія, що ще не почалась, вважається завислою і її можна перезапустити.

| Метод | Шлях | Призначення |
| --- | --- | --- |
| POST | `/api/auth/register/` | `email`, `password`; профіль необов'язковий. Завжди `202` і лист на пошту |
| POST | `/api/auth/verify-email/` | Підтвердження пошти: `uid`, `token` з листа |
| POST | `/api/auth/verify-email/resend/` | Надіслати лист ще раз (`VERIFICATION_EMAIL_THROTTLE_RATE`, типово `3/hour`) |
| POST | `/api/auth/token/` | Вхід: `email`, `password` |
| POST | `/api/auth/token/refresh/` | Новий access і новий refresh через `refresh` |
| POST | `/api/auth/logout/` | Вихід: `refresh` потрапляє в blacklist |
| POST | `/api/auth/password/change/` | `password` (поточний), `new_password`; після зміни всі refresh-токени недійсні |
| POST | `/api/auth/password/reset/` | `email`; завжди `202`, лист надходить, лише якщо акаунт існує |
| POST | `/api/auth/password/reset/confirm/` | `uid`, `token` з листа й `new_password`; посилання одноразове |
| GET, PATCH, DELETE | `/api/auth/me/` | `target_position`, `experience_level`; `email_verified` лише для читання. DELETE з `{"password": "..."}` видаляє акаунт разом із сесіями, питаннями й файлами експорту |
| GET, POST | `/api/sessions/` | Список / створення з `name` |
| GET, PATCH, DELETE | `/api/sessions/{id}/` | Перегляд, назва, видалення |
| POST | `/api/sessions/{id}/import/` | JSON `{"text":"Питання 1\nПитання 2"}` або multipart `file` |
| POST | `/api/sessions/{id}/generate/` | Генерація: тіло порожнє або `{"mode":"missing"}` — лише питання без AI-відповіді; `{"mode":"all"}` — усі заново |
| GET, POST | `/api/sessions/{id}/questions/` | Картки з пагінацією / додати одне питання в кінець: `{"text": "..."}` |
| POST | `/api/sessions/{id}/reorder/` | Новий порядок: `{"ids": [3, 1, 2]}` — id усіх питань сесії, кожне один раз |
| GET, PATCH, DELETE | `/api/questions/{id}/` | `text`, `user_answer`; `ai_parts`, `ai_error` лише для читання |
| GET | `/api/sessions/{id}/export/` | Завантаження UTF-8 TXT |
| POST | `/api/sessions/{id}/exports/` | PDF/DOCX: `{"format":"pdf"}` або `{"format":"docx"}` |
| GET | `/api/sessions/{id}/exports/{export_id}/` | Статус експорту і `download_url` |
| GET | `/api/sessions/{id}/exports/{export_id}/download/` | Завантаження готового файлу |

Списки мають поля `count`, `next`, `previous`, `results`; наступна сторінка — `?page=2`. Статус сесії читається через GET: `created → processing → ready / failed`. Відповідь 202 означає прийнятий запуск, а не гарантований успіх AI; перевіряй `status` і `error_message`. Під час обробки зміни карток (редагування, додавання, видалення, перестановка), видалення сесії, повторний запуск та експорт повертають 409. У сесії може бути до 50 питань і після імпорту, і після додавання по одному. Додане питання переводить сесію в `created`, і `generate/` без `mode` згенерує лише його. Після видалення чи перестановки номери (`order`) завжди йдуть підряд з 1. Невдала публікація в чергу повертає 503 і встановлює `failed`, квота при цьому не списується.

Gemini відповідає JSON за схемою (structured output), і картка має ці частини окремо в `ai_parts`: `explanation` (просте пояснення), `example`, `interview_answer` (відповідь для співбесіди), `common_mistake`. `example` і `common_mistake` можуть бути порожніми. `ai_answer` — ті самі частини, зібрані в один текст із заголовками; його використовують `answer`, TXT- і PDF/DOCX-експорт. У відповідей, згенерованих до появи частин, `ai_parts` дорівнює `null`, а текст лишається в `ai_answer`. JSON, що не відповідає схемі, вважається невдалою відповіддю на це питання.

Якщо Gemini не дав придатної відповіді на окреме питання (порожня відповідь, блок безпеки, обрізання на ліміті токенів), генерація переходить до наступного: таке питання отримує текст причини в `ai_error`, попередня відповідь, якщо була, залишається, а сесія завершується як `ready` з `error_message` «Не вдалося згенерувати відповіді на N з M питань». Наступний запуск `mode=missing` повторить лише питання без відповіді. Помилки, що повторювались би для кожного питання (ключ, модель, мережа, вичерпані повтори), як і раніше, зупиняють запуск зі статусом `failed`. Обрізана відповідь не зберігається: у моделей із thinking роздуми теж витрачають `AI_MAX_OUTPUT_TOKENS` (типово 8192); `AI_THINKING_BUDGET` задає бюджет роздумів (`0` вимикає їх там, де модель це дозволяє).

PDF/DOCX-експорт асинхронний: `POST .../exports/` повертає 202 і запис зі статусом `pending → processing → ready / failed`; опитуй `GET .../exports/{export_id}/`, доки не з'явиться `download_url`. Worker надсилає питання й відповіді в Exporter service (`EXPORTER_URL`, типово `http://127.0.0.1:8002`, таймаут 60 с) і зберігає файл у `media/exports/`. Якщо сесія з тим самим вмістом уже експортується або експортована в цей формат, повертається 200 з наявним записом замість нового файлу. Під час генерації експорт повертає 409, сесія без питань — 400. Експорт, що висить у `pending`/`processing` довше 10 хвилин (`EXPORT_STALE_AFTER`), або `ready` без файлу на диску не перевикористовується: новий запит створює новий файл. Частоту створення обмежує `EXPORT_THROTTLE_RATE` (типово `10/minute` на користувача).

`user_answer=null` повертає показ AI-відповіді; `user_answer=""` навмисно залишає відповідь порожньою. Зміна тексту питання очищує його AI-відповідь і повертає сесію в `created`. За замовчуванням генерація відповідає лише на питання без AI-відповіді (нові, змінені або ті, що впали з помилкою), тож зміна одного питання коштує одного виклику AI; якщо таких питань немає, повертається 400. `mode=all` оновлює всі AI-відповіді сесії. Кожна відповідь зберігається одразу, тож після помилки готові відповіді лишаються. Кожен виклик AI повторюється до 3 разів із паузою.

## Перевірки

```powershell
.\venv\Scripts\python.exe manage.py test --settings=config.test_settings
.\venv\Scripts\python.exe manage.py makemigrations --check --dry-run --settings=config.test_settings
```

Локальні тести використовують окрему SQLite-базу в пам'яті. Зовнішній SDK Gemini заміняється через `unittest.mock` лише всередині тестів; у застосунку генерація завжди звертається до Gemini. CI запускає тести на PostgreSQL. Перевіряються JWT, повний сценарій, ізоляція користувачів, валідація файлів, помилки AI/черги, відсутня конфігурація та збереження правок. Живі Gemini, Redis, Docker і конкурентні блокування PostgreSQL потребують окремого інтеграційного запуску.

Якщо worker впав, Celery доставить задачу повторно (`acks_late`). Сесія, яка 10 хвилин (`GENERATION_STALE_AFTER`) не зберегла жодної відповіді, вважається завислою: її можна запустити повторно або видалити без 409. Задача обмежена 30 хвилинами. Для production ще потрібні обмеження частоти AI-запитів, контроль бюджету й перевірка налаштувань розгортання.
